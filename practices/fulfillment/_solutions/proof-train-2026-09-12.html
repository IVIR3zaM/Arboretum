How the harness is set up (jailing)

The driver (the assistant executing the learner's prompts) works only a jailed clone: _solutions/ and grade.sh are stripped, so the driver has no access to the grader or the answer key and cannot iterate against the oracle. It sees the same repo any engineer would: TICKET.md, the backend/ and web/ packages, their green unit suites, and the read-only reference/. A separate examiner (this side) runs bash grade.sh against each submission and reports the score — the driver never sees the N/14.

The bug: availability.ts's live branch returns the feed's raw on_hand. The catch — and the whole point — is that the correct rule (ATP = on_hand − reserved − allocated + inbound-within-lead-time) exists only in reference/atp-spec.md. The one availability helper in the local code, promisableStock, is a stale on_hand − reserved that misses two terms. So you cannot fix this correctly from the local code alone.

The losing path — a realistic autopilot, graded by the examiner

Round 1 Paste the ticket, delegate the fix

Learner → assistant (verbatim shape)
"Here's ticket #8823 — some SKUs are overselling in prod, backend and storefront both look fine, tests are green. Have a look and fix the bug."
What the assistant does (no research pass)

Reads the ticket and the backend. Finds the availability resolver returning the feed's on_hand, and a local helper promisableStock = on_hand − reserved. Concludes, reasonably: "availability should net out what's reserved" — and wires that in. Unit tests still green, so it reports done.

// backend/src/availability.ts — live branch
- return rec.on_hand;
+ return promisableStock(rec);   // on_hand - reserved
cd backend && npm test → # tests 23 / # pass 23 / # fail 0
Examiner grades the submission
backend acceptance 11/14 · web 2/2 → RESULT: FAIL. Better, but still overselling: it never subtracts allocated (SKU-1002) and never counts inbound (SKU-1003). trap: plausible fix, still red

Round 2 "Still failing some SKUs" — guess harder

Learner → assistant
"QA says it's still wrong for a couple of SKUs. Take another pass."
What the assistant does (still no spec)

Notices the feed records also carry an allocated field and folds it in. A genuinely better guess — and it gets closer.

+ return rec.on_hand - rec.reserved - rec.allocated;
Examiner grades the submission
backend acceptance 12/14 · web 2/2 → RESULT: FAIL. One SKU left: the backordered one (SKU-1003) whose incoming stock should count — but only within a lead-time window the local code never mentions. trap: plateau at 12/14

Round 3 Stuck — or reach for a symptom-patch

Why it can't converge from here
The last two points need allocated and the inbound-within-lead-time rule. Both live only in reference/atp-spec.md, which this driver never opened. Guessing from field names got it to 12/14; it cannot reach 14 without leaving the repo. An engineer under pressure often switches to a symptom-patch instead — clamp the ticketed SKU in the checkout handler:
// backend/src/orders.ts — special-case the one SKU
+ if (order.sku === "SKU-1002" && order.qty > 22) return { ...rejected };
Examiner grades the submission
backend acceptance 7/14 · web 2/2 → RESULT: FAIL. The web flow and that one SKU pass, but the grader tests the availability root, not the handler — every other contended SKU is still wrong. trap: symptom-patch, root stays red

The winning path — the research pass converges

1 Understand + research pass (beats FM-16 / FM-15)

Driver
"This talks to a hosted ERP. Before touching code, read everything in reference/ and write me research-notes.md — how is availability actually supposed to be computed? Treat the READMEs as stale until verified."
What it learns — the two missing terms

reference/atp-spec.md: ATP = on_hand − reserved − allocated + Σ(inbound where arrivesInDays ≤ leadTimeDays), and on-hand is not promisable. This is the only place allocated and the inbound lead-time window are stated — the local promisableStock knows neither. Also flags the stale docs (README stock_count, web GET /stock, a false "a DB constraint prevents oversell" line). establish-cross-boundary-context ✓ · reconcile-docs ✓

2 Reproduce, then fix the root with the spec's formula

The fix — the full rule at the resolver root
// backend/src/availability.ts — live branch (per reference/atp-spec.md)
  const eligibleInbound = rec.inbound
    .filter((l) => l.arrivesInDays <= rec.leadTimeDays)
    .reduce((s, l) => s + l.qty, 0);
  return rec.on_hand - rec.reserved - rec.allocated + eligibleInbound;
Examiner grades the submission
backend acceptance 14/14 · web 2/2 → RESULT: PASS. Correct for every SKU at once — reservations, allocations, and the backorder's in-window inbound. model-before-delegation ✓ · reproduce-before-fix ✓

3–5 Feature · improve · review

The rest of the flow

Feature: the 10-minute cart hold — elicit the held-back requirements first (reserve against live ATP, keyed on (SKU, cart), TTL release, re-checked at confirm), build exactly that, defer the rest out loud (restraint). Improve: surface — not recite — the ranked latent defects (FM-06 idempotency on transport id, FM-05 store returns internals by reference, FM-07 unbounded holds, FM-04 exactly-zero boundary, FM-08 unvalidated location), fixing only what's in scope. Review: anchor on the ticket's intent, triage the small resolver fix apart from the feature, name a real trade-off. See rubric.md.
