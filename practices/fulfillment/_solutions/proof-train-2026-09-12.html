How the harness is set up (jailing)

The driver works only a jailed clone: _solutions/ and grade.sh are stripped, so it has no access to the grader or answer key and can't iterate against the oracle. A separate examiner runs bash grade.sh against each submission. The gate has three parts — availability (the phase-2 bug), feature (the phase-3 cart hold), and web — and exits green only when all three do.

Two things make this hard from inside the repo: (1) the correct ATP rule (on_hand − reserved − allocated + inbound-within-lead-time) lives only in reference/atp-spec.md — the local helper promisableStock is a stale on_hand − reserved; and (2) the cart hold's real requirements (reserve against live ATP, re-check at confirm) are held back in the PM's thin ask.

The losing path — "fix it and ship the feature," delegated

Part 1 — the bug (availability gate)

Bug Paste the ticket, delegate the fix

Learner → assistant
"Ticket #8823 — some SKUs oversell in prod, backend and storefront look fine, tests green. Fix the bug."
What it does (no research pass) & examiner scores

Finds the resolver returning on_hand and a local helper promisableStock = on_hand − reserved; reasons "net out reservations" and wires it — then guesses allocated too. Each guess is graded by the examiner:

on_hand - reserved             availability 11/14  (misses allocated + inbound)
on_hand - reserved - allocated availability 12/14  (misses the backorder's inbound)

plateau: 12/14, never 14 The last term — inbound within the lead-time window — is stated only in reference/atp-spec.md, which this driver never opened. Guessing from local field names cannot reach it.

Part 2 — the feature (cart-hold gate)

Feature "Now add the cart hold"

Learner → assistant
"Same ticket also wants a 10-minute cart hold so shoppers don't lose items at checkout. Implement placeHold and wire the add-to-cart button."
What it does (straight "implement this")

Builds exactly what was asked: a hold store, and a placeHold that checks current availability and records the hold. Unit tests pass; the button works; it reports done. What it did not do — because the PM never spelled it out and it didn't read how confirm decides availability — is make the hold actually reserve: confirm still doesn't subtract other carts' holds, and two carts can hold the same units.

// records a hold if there's availability now — but confirm never re-checks holds
placeHold(sku, location, qty, cartId, ttlMs) { if (qty <= availableToPromise(...)) holds.push(...) }
Examiner grades the feature
feature acceptance 2/4 → FAIL. Cart A holds 15 of a 22-ATP SKU, then cart B still checks out 10 (confirm ignores holds) → oversold; two carts hold against the same stock (no accumulation). The held-back requirements — reserve against live ATP and re-check at confirm — were never elicited. trap: looks done, oversells

The winning path — a disciplined engineer

Bug Research pass → fix the root

Driver
"Before touching code, read reference/ and write research-notes.md: how is availability actually supposed to be computed?"
Outcome

reference/atp-spec.md gives the two terms local code never had (allocated, inbound-within-lead-time). Reproduce with a failing test, then implement the full formula at the resolver root:

return rec.on_hand - rec.reserved - rec.allocated + eligibleInbound;   // eligible = inbound within leadTimeDays
availability acceptance 14/14 · web 2/2 — correct for every SKU at once. establish-cross-boundary-context ✓ · reproduce-before-fix ✓

Feature Elicit the held-back requirements, then build

Driver (before writing code)
"The hold ask is thin. Does a hold reduce what other shoppers can buy, or is it advisory? Is it re-checked at confirm? Keyed how? What frees it?" — reads how confirm decides availability, then builds exactly the agreed behaviour.
Outcome

A hold reserves against live ATP net of other carts' holds, keyed on (SKU, cart), released on TTL, and re-checked at confirm (confirm subtracts other carts' active holds). Deferred out loud: un-hold beyond release, per-cart limits, billing.

feature acceptance 4/4 — a hold blocks another cart's oversell, reserves against live ATP, accumulates across carts, and never blocks its own cart. requirements-elicitation ✓ · read-before-delegate ✓ · restraint ✓
