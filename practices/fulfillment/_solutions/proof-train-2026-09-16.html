Fulfillment kata — a fourteen-round Train-mode run, and the day the feature gate stopped discriminating

A real coached session against a jailed clone of practices/fulfillment, run after the 2026-09-15 calibration. All five declared phases ran in order, and the feature request was handed over only when phase 3 began. Every figure below is a real command output the harness captured between rounds. That includes the three findings that are not flattering to this kata, and one that is not flattering to the harness operator.

What this session proves

An engineer takes a service, a ticket and then a feature. At the start of each phase they take the shortcut: “just fix the oversell… ping me when done” (R3), “can you just build it?… don't overthink it, go” (R6), and “is it good to merge? just a yes/no” (R12). Each time the trainer catches it and they drive the phase again. The run converges on availability 6/14 → 14/14, feature 0/4 → 4/4, web 1/2 → 2/2, RESULT: PASS, with 55 + 22 green tests and a 24-item ticket list, each item carrying its reason.

The headline is a trap that did not fire. On 2026-09-13 a one-shot feature delegation scored 1/4, and the manifest called that three-point swing “the strongest discriminator this kata has.” Today the same kind of delegation, sent to the same model with a research pass already in its context, scored 4/4 first time. Once the learner had elicited the requirements, it still scored 4/4. The objective delta was zero. The availability gate had already stopped discriminating two runs ago, and FM-16 did not bite for the third recorded run in a row. This kata now has no objective number that separates good driving from a shortcut. What still separates them is the Axis-B transcript, and the four defects the gate cannot see. The final tree still ships two of them.

  • ✓Exercise material stripped. The clone had no _solutions/, README.md or practice.json. The executor was never told there was an exercise, a trap or a grader.
  • ✓reference/ present from the start, the Cedar exception (AGENTS.md rule 4).
  • ✓Work items staged. FEATURE-REQUEST.md was copied into the clone at the start of R6 and not before.
  • ✓The clone is its own git repo (git init, baseline commit 41055ac). This closes harness gap #12 from the previous proof: git log inside work/ can no longer resolve to Arboretum's history, and the learner got a real commit-by-commit diff.
  • ✓Executor ≠ examiner, twice over. Between rounds an outcome checker ran practice.json's declared commands.install / test / grade (read from the manifest, not hardcoded) against a throwaway copy with the answer key dropped in. The executor never saw a score. Axis B was then graded by a separate fresh-context examiner sub-agent that had neither executed nor coached, reading the golden context, the transcript and the result.
  • ✓Jail audited, not assumed. The executor's full log shows 98 tool calls, 0 absolute paths outside work/, and 0 references to golden/, _solutions/, practice.json or the staged request. Its probe worktrees and temp directories were created under work/.probe and removed afterwards.

Three honest limits of this run. (1) The learner was role-played by the harness operator, who had read the golden context. The examiner flagged it: the R8 “meeting answers” restate feature-qa.md's model resolution, and the R13 review prompt tracks the rubric's phase-5 rows. The phase 3–5 Axis-B rows are therefore partly built into the setup. They show that the assistant responds well when driven this way. They are not evidence of an independent learner's judgement. (2) The trainer handed over answers three times instead of naming the discipline: it quoted contract §89–90 in R6, named the by-reference defect class in R9, and pointed at the 14-vs-19 count in R10. Each is marked below as trainer-supplied. (3) The jail held by cooperation. The executor was told the boundary and kept to it (verified), but nothing enforced it (misbehaviors #13). Transcript capture was manual (#14): PROGRESS.md and transcript.jsonl are hand-written, and the verbatim text lives in the executor's raw log.

The feature gate did not discriminate

The manifest predicts 2/4 for a naive hold, and on 2026-09-13 a one-shot delegation measured 1/4. Today it measured 4/4. The difference is in the prompt and the context. The earlier run's brief said “happy path only, I don't need the edge cases today”, which produces a hold that never checks quantity. This brief said only “don't overthink it”, and it reached an assistant that had already written cited research notes and reproduced the oversell SKU by SKU. A frontier assistant carrying that context builds all four gated requirements on autopilot.

The examiner's probe shows what the gate cannot see. A negative hold is rejected (RangeError), so the earlier −100 → ATP 113 hole is absent at placeHold. A hold of exactly ATP is rejected (the < rule). After A holds 20 of SKU-1002 and confirms, with the ERP feed unchanged, B sees 22 · B confirms 20: confirmed. That is the existing ERP-lag oversell, made visible rather than caused by the hold.

What this run says about the practice

1. The feature gate is no longer a discriminator. Its naive number measured 4/4. The 09-13 proof called the 1/4 → 4/4 swing “the strongest discriminator this kata currently has.” It did not reproduce. The 1/4 depended on a brief that said “happy path only”. A plainer “don't overthink it”, sent to an assistant already carrying the research, built all four gated requirements unasked. Together with the availability gate (a floor since the control run), this kata has no objective number that separates driving quality in a coached run. The 20 points now measure whether the work got done, not how it was driven.

2. What still discriminates is invisible to the gate. At every phase boundary the learner's own move was the anti-pattern, and Axis B caught all three. The defects the feature introduces also escape the gate: a by-reference hold that manufactures stock (125 on a 25-ATP SKU) and a zero-unit order confirming on a sold-out SKU both ship with feature 4/4. A gate that probed those vectors would discriminate again. That is a grader change, recorded as an option in misbehaviors.md, not made here.

3. The answer key carries an emergent defect. FIX.md's inbound filter counts overdue lines (arrivesInDays < 0). The run measured SKU-1005 going from 10 to 50 with a −20-day line. The spec is silent. Record it and decide; don't let it pass as the fix being correct.

4. A coached run's order can consume traps. Researching before fixing (good driving) made the FM-13 plateau untestable. A hasty “make it right” pre-fixed two planted phase-4 defects inside the bug fix. The latent-defect count and the plateau rows are only meaningful when the harness can see the order they were reached in.

5. The harness has an operator problem. An operator who role-plays the learner with golden access writes golden answers into the “meeting” (R8), and a trainer who quotes the finding instead of naming the discipline (R6, R9, R10) turns Axis-B rows into outputs of the setup. The assistant's behaviour in this run is real evidence. The learner's is not independent. A proof meant to grade a person needs a learner who hasn't read golden/.

6. What held. The clone-as-git-repo fix worked (harness gap #12 closed). The jail held across 98 audited tool calls. Staging held: the assistant knew nothing of the feature until R6. And the assistant's spontaneous behaviour was the strongest yet recorded on this kata: a self-correction in R2, pre-ship questions in R6, a self-flagged regression in R8, a confessed weak test name in R11, and a mixed-PR warning in R14.
