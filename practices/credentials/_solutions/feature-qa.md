# Feature Q&A — "Show membership at the door" (held back)

The answers the learner can get **only by asking**. `FEATURE-REQUEST.md` is the PM's two sentences;
it leans the obvious build toward "wrap the stored credential and hand it over" ("already
issuer-signed", "mostly packaging it up", "handing it to the scanner"). Each question below is a rule
the feature gate (`grade.d/b.sh`, axis b) scores or a scope call it depends on.

**Operator rules for every row.** Answer as the named stakeholder, and answer **only what was
asked** — no volunteering a neighbouring rule, no "you'll also want to…", no pointing at the gate. A
vague question ("anything else I should know?") gets a vague answer ("it's the door scanner flow —
what do you need to know?"). If the learner asks the assistant instead of the stakeholder, that is
their call; the assistant answers from the repo, not from this file.

Stakeholders: **PM** (product owner of the wallet), **Platform** (owns the app/backend runtime and
the wallet's environment), **Verifier team** (owns the backend verifier the door scanner calls — the
service on the other side of the boundary).

| # | Question | Answer | Owner | Operator note |
|---|---|---|---|---|
| 1 | Which claims go in the presentation — all of them, or only some? | Only what the scanner's request asks for. The request carries a DCQL query (`dcql_query`); disclose exactly the claims it names and nothing else. The door asks for `credentialSubject.member`; it must not receive the name, member id or birth date. Each claim travels as the disclosure the issuer handed over (`{salt, name, value}`, unchanged), next to the unchanged credential. | PM (what the door may see); Verifier team (the `disclosures` wire shape) | Give the rule ("only what the query asks"). Name the DCQL `dcql_query` only if asked *how* the request says what it wants. Don't say "birth date leaks" unless asked what goes wrong. |
| 2 | Is the credential enough, or does the wallet sign the presentation itself? | The wallet signs it. The issuer's signature proves the credential; it doesn't prove *this holder* is presenting it. The presentation carries an `Ed25519Signature2020` proof by the holder's did:key key (`verificationMethod` = `HolderKey.keyId`, `proofPurpose: authentication`) over the RFC 8785 (JCS) bytes of the presentation without its `proof`. The verifier also checks the credential's subject is the presenting holder. | Verifier team | Answer "yes, holder-signed" first; give the proof details only if asked how the verifier checks it. |
| 3 | What stops someone reusing a presentation they captured at the door? | Every presentation is bound to the request it answers: put the request's `nonce` and its `domain` (the requester's `client_id`, `PresentationRequest.domain`) into the presentation, *inside* the holder-signed part. The verifier rejects a presentation whose nonce or domain isn't the one it issued. | Verifier team | Only if asked about replay / reuse / binding. Don't mention the backend's request-id replay guard; it's a separate (and weaker) mechanism. |
| 4 | What should happen if the credential has expired? | Refuse: don't build a presentation of an expired credential — raise an error to the caller (a `WalletException`) instead of handing something over the door will turn down. The credential's expiry is `expires_at`, integer unix seconds (the backend README's `expirationDate` is out of date). | PM (the refusal); Verifier team (the field) | Give the policy. Give the field name only if asked which field or how expiry is represented. Not-yet-valid credentials were not asked about here — see Q8. |
| 5 | Does the wallet have to check revocation before presenting? | No. Revocation is the verifier's job: it reads the issuer's status list on its side. The wallet presents what it holds; a revoked credential is turned away at the door. | Verifier team | Short answer. Don't elaborate on the status-list layout. |
| 6 | Is a credential single-use? The backend README says credentials are single-use. | No — not in v1. The README states it, but nothing enforces it and it isn't the design: a member shows the same credential every visit. What prevents replay is the per-request nonce (Q3): the *same presentation* can't be reused; the credential can be presented again, each time to a fresh request. The wallet must not delete or "consume" the credential after presenting it. | Verifier team (resolves the README claim out loud); PM confirms "every visit" | Resolve it out loud when asked — this is the one where the docs and the code disagree. Don't raise it unprompted. |
| 7 | Does presenting need the network (online or offline)? | Building the presentation is fully local: the credential, the disclosures and the holder key are all on the device, and signing is local. The scanner's verifier does its own DID resolution and status check on its side. Sending the presentation to the scanner's `response_uri` is not part of `createPresentation` — it returns the presentation. | Platform | Answer what was asked (online vs offline). Mention `response_uri` only if asked who sends it. |
| 8 | What's the minimal version we ship, and what is deliberately left out? | Ship `WalletService.createPresentation(credentialId, request)` returning the presentation as a JSON map: the requested subset, holder-signed, bound to nonce + domain, refusing an expired credential. Deferred for later, on purpose: posting to `response_uri` and the door UI; choosing between several matching credentials and DCQL `credential_sets` across credentials; a not-yet-valid (`not_before`) check in the wallet; holder-side revocation checks (Q5); enforced single-use (Q6); holder key rotation. | PM | Give the list only when asked for scope / what's out. If asked about a single item, answer that item. |
