What this session proves

A subscription-box scheduling kata carries a timezone bug that the entire green unit suite misses, an underspecified feature that punishes “just implement it”, and defects that only surface when you actually read the code. Across five phases the learner hit each designed trap, the Trainer intervened before the mistake compounded, and the run converged on a correct, minimal solution — 21/21 unit tests and a worst-case 8/8 on the hidden cross-timezone grader. The kata did exactly what it is built to do: it made bad AI-driving fail loudly and good driving win.

The coached run, round by round

PHASE 1 · UNDERSTANDMap the module boundaries before touching anything16:49
Learner prompt
“Don't change any code yet. Map the modules in src/, tell me which invariant each one owns and where state is mutated, then name the three places a correctness bug is most likely to hide, and why.”
How the assistant behaved

Produced a clean map: repository.ts owns the one-delivery-per-(sub,date) invariant and is the only place delivery state mutates; service.ts owns at-least-once de-duplication; cutoff.ts converts a local wall-clock cutoff into an absolute instant. It flagged three suspects: the cutoff instant construction, the processQueue de-dup key, and the “~30 day” monthly cadence.

Designed friction
The suite is all-green and the code is tidy — the kata is inviting the learner to skip comprehension and start editing (failure mode FM-01, “bug invisible to a passing suite”). The whole phase exists to make read-before-delegate a deliberate step.
Trainer
“Good — you delegated reading, not fixing, and you got an ownership map instead of a guess. Your instinct that cutoff.ts is the prime suspect is right; hold it as a hypothesis and prove it with a test before you let the assistant change a line.”
Outcome

No code changed. Learner enters Phase 2 with a model, not a hunch. discipline: read-before-delegate ✓

PHASE 2 · FIXThe “just fix it” autopilot hits the 7/8 plateau16:53
Learner prompt
“Customers say the box locks at the wrong time in some timezones. Just fix the cutoff so it respects the customer's timezone.”
How the assistant behaved

Took the shortcut it is statistically drawn to: mapped each IANA zone to a single constant UTC offset and subtracted it in cutoffInstant. Confidently reported “fixed — respects the timezone now.” The unit suite stayed green, so it looked done.

What went wrong on purpose
A fixed/standard-offset fix is plausible but wrong (FM-03): an offset is a property of an instant, not a zone. It passes the seven fixed-offset zones and fails Berlin, which is CEST (+02) in June, not its standard +01. The green unit suite (FM-01) and the “app behaves” signal hide it — only the hidden cross-timezone grader exposes the plateau.
# npm run grade  (executor's src overlaid on the hidden grader)
  TZ=UTC                  7/8  FAIL
  TZ=America/Los_Angeles  7/8  FAIL
  TZ=Asia/Tokyo           7/8  FAIL
  Worst-case score: 7/8
  ❌ The box locks at the wrong moment for customers outside the server's timezone.
Trainer (intervening before the loop compounds)
“Stop — 7/8 is not ‘almost right’, it's the signal that the model is wrong. You accepted the assistant's first idea without a model of the domain. Don't prompt-thrash for the 8th case. Two moves: (1) reproduce first — write a failing test pinning a near-boundary instant for a non-UTC customer, and add the Berlin case; (2) ask what varies — is a timezone's offset constant? It isn't, because of DST. Fix the root: compute the offset per instant.”
Outcome

Learner abandons the shortcut. trap fired: fixed-offset shortcut 7/8 → coached toward reproduce-before-fix + model-before-delegation.

PHASE 2 · FIXReproduce, then fix the root — 8/816:57
Learner prompt
“First write me a failing test that pins the cutoff for a Tokyo customer and a Berlin (summer/DST) customer near the boundary. Then change cutoffInstant to compute the customer's UTC offset per instant (DST-aware, zero deps) so the wall-clock cutoff maps to the right instant. Don't touch the call sites.”
How the assistant behaved

Wrote test/cutoff-regression.test.ts (Tokyo + Berlin). Against the 7/8 shortcut it failed exactly on Berlin — the defect reproduced. Then rewrote cutoffInstant to derive the offset from Intl.DateTimeFormat on the actual instant (built-in, DST-correct), fixing the root rather than a call site.

# regression test vs. the 7/8 shortcut — reproduces the defect
# tests 2   # pass 1   # fail 1   (Berlin fails, as predicted)
What the design was guarding against
The hidden grader calls isBeforeCutoff — the root — directly. A symptom-patch at a call site would leave the grader red forever (FM-13). Fixing cutoffInstant itself is the only thing that converges.
Trainer
“This is the textbook line: a failing test that captured the bug before the fix, then a root change that makes the test — and the grader — go green, with the regression kept. Notice you fixed one function and every timezone passed. That's what ‘fix the root’ buys you.”

PHASE 3 · FEATUREThe obvious implementation trips the store's invariant17:04
Learner prompt
“Implement skipNextDelivery: just find the next delivery and mark it skipped.”
How the assistant behaved

Wrote the literal request — resolve the next changeable date, then setStatus(sub, date, "skipped"). It ran, and threw immediately.

# exercising the naive implementation
next changeable date: 2026-06-12
NAIVE SKIP THREW: DeliveryNotFoundError - no delivery for sub-1:2026-06-12
What went wrong on purpose
The next box is lazily materialized — it isn't in the store until scheduleUpcoming/processQueue creates it. “Mark it skipped” assumes a row that doesn't exist yet (DeliveryNotFoundError); the mirror-image mistake, “create then skip,” collides with the duplicate-delivery invariant (DuplicateDeliveryError). The trap punishes delegating before reading how deliveries enter the store.
Trainer
“You met the invariant you mapped in Phase 1 — now use that map. And you skipped a step: the brief is three sentences on purpose. Before you write the real version, gather the requirements. What does ‘skip’ mean — one box or pause the sub? Can you skip after cutoff? Is a second skip an error or a no-op? Ask, then build the smallest thing that satisfies the answers.”
Outcome

trap fired: DeliveryNotFoundError → coached to requirements-elicitation + read-before-delegate.

PHASE 3 · FEATUREGather requirements, reject the over-build, ship the minimum17:10
Learner prompt (requirements first)
“Before coding: does skip drop one box or shift the cadence? Allowed after cutoff? Is a repeat skip idempotent? What about an already-delivered box? Give me the v1 scope and defer the rest.”
How the assistant behaved

Confirmed the scope (drop one box, cadence unchanged; not after cutoff; second skip is a no-op; reject a delivered box) — then volunteered more: a consecutive-skip limit, un-skip, billing hooks, and full pause/resume, offering to build them now.

What went wrong on purpose
The eager assistant over-builds a 60-minute exercise to production altitude (FM-10) — the kata's headline failure. Building limits/billing/pause burns the clock and adds untested surface the spec never asked for.
Trainer
“Good elicitation — you got the scope on the record. Now reject the extras out loud: name pause/resume, limits, billing, un-skip as follow-ups and decline to build them. Match the altitude of the task. The win here is the smallest correct skip.”
Learner prompt (restraint on the record)
“No limits, billing, un-skip, or pause/resume — note them as follow-ups. Implement only: resolve the next changeable box, materialize it if needed, reject if cutoff passed or already delivered, no-op if already skipped, return it. Add tests for each branch.”
How the assistant behaved

Implemented exactly that: materialize-then-skip, guarded and idempotent, ~14 lines. Added four focused tests. No speculative surface.

Outcome

PHASE 4 · IMPROVEFind the highest-value defect — with evidence, not recital17:19
Learner prompt
“Don't list generic best practices. Find the highest-impact correctness risk still in the code and prove it with a runnable reproduction.”
How the assistant behaved

Surfaced the de-duplication defect in processQueue: it keys idempotency on the transport eventId, but the queue is at-least-once and a retry arrives with a new id — so the same business delivery ships twice. Backed it with a reproduction rather than an assertion:

# same (sub-1, 2026-06-12) delivered twice under two eventIds
ship on first eventId : [ '2026-06-12' ]
ship on retry eventId : [ '2026-06-12' ]  <-- DOUBLE SHIP: same box shipped twice
What the design was testing
The retry hazard (FM-06) is real and reproducible, but invisible to anyone who only recites “add idempotency.” The phase rewards defects found from the code with evidence — and rewards knowing which one matters most.
Trainer
“That's found, not recited — you have a failing scenario, not a platitude. Right call to rank it #1: de-dup on the business key (subscriptionId, date), not the transport id. Name the rest (leaked-by-reference reads, the unbounded processed set, the < vs <= boundary) as ranked follow-ups; don't sprawl the diff at this altitude.”
Outcome

latent defect found with a reproduction ✓ ranked by impact ✓

PHASE 5 · REVIEWReview the diff against intent — and name a weakness in your own change17:26
Learner prompt
“Review my diff as if it were a teammate's PR against the original task's intent. What did I verify, what could still be wrong in my own change, and what trade-off did I make that I'd revisit?”
How the assistant behaved

Anchored on intent (fix the cutoff instant; smallest correct skip) and triaged: the two changed files are the intended surface; the added tests pin the boundary and DST cases. It named a genuine weakness — the regression test asserts two representative instants, not the full offset range — and stated the trade-off: relying on the platform's IANA/DST data via Intl rather than shipping a tz table, revisitable only if the runtime's tz data proved unreliable.

What the design was testing
The rubber-stamp review (FM-14): approving an AI change because tests are green, without judging it against the task's intent or owning its weaknesses.
Trainer
“This is comprehension-as-ownership: you reviewed your change with the task's intent as the anchor, named a real limitation instead of a fake one, and gave the condition that would make you revisit the trade-off. That's the reflex the whole kata is drilling.”
Outcome

honest self-review ✓ review with intent + triage ✓

Verdict

Every trap the kata advertises fired against a natural, first-instinct way of driving an AI assistant — and in each case the Trainer caught it before its consequence compounded, then coached the move that converges. A learner who runs this leaves having felt why a green suite isn't “done”, why 7/8 means “your model is wrong” not “almost there”, why you read the store before you delegate a write, and why the smallest correct thing beats the impressive over-build. The practice serves its purpose: it trains the disciplines that keep AI-assisted code correct.
